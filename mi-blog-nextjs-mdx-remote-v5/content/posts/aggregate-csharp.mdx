# 1. Primero: ¿qué problema resuelve un Aggregate?

Supongamos que tenemos:

```text
Orden de mantenimiento
    │
    ├── Actividad 1
    ├── Actividad 2
    ├── Actividad 3
    └── Actividad 4
```

Una pregunta fundamental es:

> ¿Quién tiene la responsabilidad de garantizar que esas actividades se puedan agregar, modificar o eliminar correctamente?

Si cualquier parte de la aplicación puede hacer:

```csharp
orden.Actividades.Add(...);
```

entonces estamos dejando que cualquier código pueda modificar el estado interno de la orden.

Eso es peligroso en DDD.

Queremos algo como:

```csharp
orden.RegistrarActividad(actividad);
```

La propia `OrdenMantenimiento` controla las reglas.

Ahí empieza a aparecer el concepto de **Aggregate**.

---

# 2. ¿Qué es un Aggregate?

Un Aggregate es:

> **Un conjunto de objetos del dominio que se considera una unidad de consistencia y que tiene una única puerta de entrada: el Aggregate Root.**

Visualmente:

```text
          AGGREGATE
┌──────────────────────────────┐
│                              │
│    OrdenMantenimiento        │
│       │                      │
│       ├── ActividadRealizada │
│       │                      │
│       ├── ActividadRealizada │
│       │                      │
│       └── ActividadRealizada │
│                              │
└──────────────────────────────┘
             ▲
             │
       Aggregate Root
```

La raíz sería:

```text
OrdenMantenimiento
```

---

# 3. ¿Qué es Aggregate Root?

El **Aggregate Root** es la entidad principal que controla el Aggregate.

En nuestro ejemplo:

```text
OrdenMantenimiento
       │
       ├── ActividadRealizada
       ├── ActividadRealizada
       └── ActividadRealizada
```

`OrdenMantenimiento` es el **Aggregate Root**.

Las otras entidades pertenecen al Aggregate.

Una regla importante es:

> **El exterior debería interactuar con el Aggregate a través de su Root.**

Por ejemplo:

```csharp
orden.RegistrarActividad(actividad);
```

y no:

```csharp
orden.Actividades.Add(actividad);
```

---

# 4. ¿Por qué?

Porque el Aggregate Root puede proteger las reglas del negocio.

Por ejemplo:

```csharp
public class OrdenMantenimiento
{
    private readonly List<ActividadRealizada> _actividades = [];

    public IReadOnlyCollection<ActividadRealizada> Actividades
        => _actividades.AsReadOnly();

    public void RegistrarActividad(
        ActividadRealizada actividad)
    {
        if (actividad is null)
            throw new ArgumentNullException(nameof(actividad));

        _actividades.Add(actividad);
    }
}
```

Ahora nadie puede hacer directamente:

```csharp
orden.Actividades.Add(...);
```

porque exponemos:

```csharp
IReadOnlyCollection<ActividadRealizada>
```

y no:

```csharp
List<ActividadRealizada>
```

Esto conecta directamente con lo que estuvimos estudiando sobre:

```text
IEnumerable<T>
ICollection<T>
IReadOnlyCollection<T>
IReadOnlyList<T>
```

En DDD, esta protección es muy importante.

# 5. Ahora agreguemos una regla real de HVAC

Imaginemos que una orden tiene estados:

```csharp
public enum EstadoOrden
{
    Programada,
    EnProceso,
    Finalizada,
    Cancelada
}
```

Una regla podría ser:

```text
Programada
     ↓
EnProceso
     ↓
Finalizada
```

Pero no:

```text
Finalizada
     ↓
EnProceso
```

Entonces:

```csharp
public class OrdenMantenimiento
{
    public EstadoOrden Estado { get; private set; }

    public void Iniciar()
    {
        if (Estado != EstadoOrden.Programada)
            throw new DomainException(
                "La orden debe estar programada para poder iniciarse.");

        Estado = EstadoOrden.EnProceso;
    }

    public void Finalizar()
    {
        if (Estado != EstadoOrden.EnProceso)
            throw new DomainException(
                "La orden debe estar en proceso para poder finalizarse.");

        Estado = EstadoOrden.Finalizada;
    }
}
```

Aquí vemos algo fundamental:

**La entidad contiene comportamiento.**

No es simplemente:

```csharp
public class OrdenMantenimiento
{
    public Guid Id { get; set; }
    public string Estado { get; set; }
}
```

Eso sería un modelo anémico muy orientado a datos.

En cambio:

```csharp
orden.Iniciar();
orden.Finalizar();
orden.RegistrarActividad(...);
```

representa comportamiento del dominio.

# 6. ¿Quién debería modificar las actividades?

Supongamos:

```text
Orden
│
├── Actividad 1
├── Actividad 2
└── Actividad 3
```

No queremos:

```csharp
actividad.Estado = ...
```

desde cualquier lugar.

Preferimos:

```csharp
orden.RegistrarActividad(actividad);
```

o:

```csharp
orden.CompletarActividad(actividadId);
```

La `OrdenMantenimiento` controla las reglas.

Por ejemplo:

```csharp
public void CompletarActividad(Guid actividadId)
{
    var actividad = _actividades
        .FirstOrDefault(x => x.Id == actividadId);

    if (actividad is null)
        throw new DomainException(
            "La actividad no pertenece a la orden.");

    actividad.Completar();
}
```

Ahora la Orden controla quién puede modificar sus actividades.

# 8. Una regla muy importante de DDD

> **No debes pensar que cada relación de base de datos representa un Aggregate.**

Este es uno de los errores más comunes al comenzar DDD.

Por ejemplo, en SQL podrías tener:

```text
Orden
   │
   ├── EquipoId
   │
   ├── TecnicoId
   │
   └── ClienteId
```

Eso no significa que:

```text
Orden
 ├── Equipo
 ├── Técnico
 └── Cliente
```

deban formar un único Aggregate.

El diseño DDD se hace pensando en:

**reglas + consistencia + comportamiento + límites del dominio**, no simplemente en las FK de SQL.

# 11. ¿Por qué esto es diferente de un CRUD?

En CRUD normalmente pensamos:

```text
POST /ordenes
GET /ordenes
PUT /ordenes
DELETE /ordenes
```

En DDD pensamos:

```text
CrearOrden()
Iniciar()
RegistrarActividad()
RegistrarRespuesta()
Finalizar()
Cancelar()
```

La diferencia es enorme.

CRUD piensa principalmente en:

> "¿Qué datos voy a guardar?"

DDD piensa:

> **"¿Qué puede hacer el negocio y qué reglas debe respetar?"**

# 12. Una regla de oro para tus Aggregates

Quédate con esta frase:

> **Un Aggregate debe ser lo suficientemente pequeño para poder mantener su consistencia fácilmente.**

No hagamos esto:

```text
Empresa
 │
 ├── Clientes
 │    ├── Equipos
 │    │    ├── Ordenes
 │    │    │    ├── Actividades
 │    │    │    │    └── Respuestas
 │    │    │    └── ...
 │    │    └── ...
 │    └── ...
 └── Técnicos
```

y decir:

> "Todo esto es un Aggregate."

Sería enorme y problemático.

Es mejor tener varios Aggregates:

```text
Cliente
Equipo
OrdenMantenimiento
```

y definir las relaciones entre ellos mediante identificadores.

### Delegate

```text
C#
│
└── referencia a un método
```

### Entity

```text
DDD
│

```

### Value Object

```text
DDD
│
└── objeto definido por sus valores
```

### Aggregate

```text
DDD
│
└── conjunto de objetos que forman

```

```text
DDD
```

# 16. Segundo candidato: OrdenMantenimiento

```csharp
public class OrdenMantenimiento

    }
}
```

```text

        ↓
      Entity
        ↓
 Aggregate Root
```

Aquí tenemos un candidato muy fuerte.

# 19. Actividad realizada es diferente

Cuando ejecutas una orden:

```text

       │

```

Por ejemplo:

```text

120 PSI
```

No tendría sentido:

```text

```


```text

        ├── ActividadRealizada

```

Aquí `ActividadRealizada` podría ser una **Entity interna del Aggregate**.

# 23. ¿Y cómo se relacionan los Aggregates?

Podríamos terminar con algo parecido a:

```text
                    DOMAIN
                       │
       ┌───────────────┼────────────────┐
       │               │                │
       ▼               ▼                ▼
     Cliente         Equipo        ActividadCatalogo
       │               │                │
       │               │                │
       └───────────────┴────────────────┘
                       │
                       │ Ids
                       ▼
               OrdenMantenimiento
                 Aggregate Root
                       │
                       ├── ActividadRealizada
                       │       └── Respuesta
                       │
                       └── ActividadRealizada
```

La idea importante es que **no metemos todo dentro de la Orden**.

Por ejemplo, no haríamos:

```csharp
public class OrdenMantenimiento
{
    public Equipo Equipo { get; set; }

    public Cliente Cliente { get; set; }

    public Tecnico Tecnico { get; set; }

    public List<Actividad> Actividades { get; set; }
}
```

simplemente porque las tablas están relacionadas.


### Pregunta 2

> ¿Necesito garantizar una regla entre ellas inmediatamente?

Si sí:

```text
probablemente mismo Aggregate
```

### Pregunta 3

> ¿Pueden tener ciclos de vida independientes?

Si sí:

```text
probablemente Aggregates diferentes
```

### Pregunta 4

> ¿Puedo referenciarlo mediante su Id?

Si sí, muchas veces:

```text
Aggregate diferente
```

```text
│    Aggregate Root     │
└───────────────────────┘


┌────────────────────────────────┐
│     OrdenMantenimiento         │
│       Aggregate Root           │
│                                │
│  ├── ActividadRealizada        │
│  │      └── Respuesta          │
│  │                             │
│  └── ActividadRealizada        │
│         └── Respuesta          │
└────────────────────────────────┘
```

**Pero todavía no lo implementaría en código.**

Primero debemos validar esta estructura contra las **reglas reales de tu negocio HVAC**.

Y hay una pregunta especialmente importante que debemos resolver ahora:

> **¿`Actividad` representa una definición reutilizable del catálogo, mientras que `ActividadRealizada` representa la ejecución concreta dentro de una orden?**

Si la respuesta es sí, acabamos de separar dos conceptos que en un CRUD tradicional probablemente terminarían mezclados.

Ese sería nuestro **siguiente paso de modelado DDD**: definir `ActividadCatalogo`, `ActividadRealizada` y `Respuesta`, y decidir exactamente qué es **Entity, Value Object y Aggregate** en cada caso.
