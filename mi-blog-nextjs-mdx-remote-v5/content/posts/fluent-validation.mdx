# 1. ¿Qué es FluentValidation?

Es una librería que permite escribir reglas de validación utilizando C# en lugar de atributos.

En lugar de esto:

```csharp
public class CrearClienteDto
{
    [Required]
    [StringLength(100)]
    public string Nombre { get; set; }

    [EmailAddress]
    public string Email { get; set; }
}
```

escribes:

```csharp
public class CrearClienteValidator : AbstractValidator<CrearClienteDto>
{
    public CrearClienteValidator()
    {
        RuleFor(x => x.Nombre)
            .NotEmpty()
            .MaximumLength(100);

        RuleFor(x => x.Email)
            .EmailAddress();
    }
}
```

Mucho más limpio.

---

# 2. ¿Por qué no usar DataAnnotations?

Porque DataAnnotations tiene muchas limitaciones.

Por ejemplo:

```csharp
[Required]
[StringLength(100)]
```

Funciona bien...

Pero...

¿Cómo validas que un cliente exista en la base de datos?

No puedes.

¿Cómo validas dos propiedades juntas?

Difícil.

¿Cómo haces consultas?

No puedes.

¿Cómo reutilizas reglas?

Muy complicado.

FluentValidation nació precisamente para solucionar esos problemas. ([FluentValidation][1])

---

# 3. ¿Dónde vive FluentValidation?

En una arquitectura limpia:

```
Presentation
      │
      ▼
Application
│
├── Commands
├── Queries
├── Validators   ← AQUÍ
├── DTOs
├── Interfaces
└── Services

Domain

Infrastructure
```

Nunca en Domain.

Nunca en Infrastructure.

Siempre en **Application**.

¿Por qué?

Porque valida la entrada de un caso de uso.

No valida reglas del negocio.

# 5. Primer ejemplo

Supongamos este DTO.

```csharp
public class CrearProductoDto
{
    public string Nombre { get; set; }

    public decimal Precio { get; set; }

    public int Stock { get; set; }
}
```

Creamos:

```csharp
public class CrearProductoValidator
    : AbstractValidator<CrearProductoDto>
{
    public CrearProductoValidator()
    {
        RuleFor(x => x.Nombre)
            .NotEmpty();

        RuleFor(x => x.Precio)
            .GreaterThan(0);

        RuleFor(x => x.Stock)
            .GreaterThanOrEqualTo(0);
    }
}
```

Muy sencillo.

# 9. Cascade

Sin Cascade:

```csharp
RuleFor(x => x.Nombre)
    .NotEmpty()
    .MinimumLength(5)
    .MaximumLength(100);
```

Si está vacío obtendrás varios errores.

Con:

```csharp
.Cascade(CascadeMode.Stop)
```

Se detiene en el primero.

```csharp
RuleFor(x => x.Nombre)
    .Cascade(CascadeMode.Stop)
    .NotEmpty()
    .MinimumLength(5);
```

# El principio que está respetando

Aquí aparece uno de los principios SOLID.

## SRP (Single Responsibility Principle)

Cada clase debe tener una sola responsabilidad.

Entonces:

### Controller

Responsabilidad

```
Recibir HTTP
```

Nada más.

---

### Validator

Responsabilidad

```
Validar datos de entrada
```

Nada más.

---

### Handler

Responsabilidad

```
Ejecutar el caso de uso
```

Nada más.

---

### Repository

Responsabilidad

```
Persistir información
```

Nada más.

Observa cómo cada pieza tiene un objetivo único. Esto hace que el código sea más fácil de mantener, probar y extender.

# Flujo correcto en una arquitectura moderna

En TribuSoft construiremos exactamente este flujo:

```text
                HTTP Request
                     │
                     ▼
             PersonaController
                     │
                     ▼
          CrearPersonaCommand
                     │
                     ▼
     CrearPersonaValidator
                     │
        ¿Es válido?
          │        │
         No       Sí
          │        │
          ▼        ▼
400 Bad Request   CrearPersonaHandler
                      │
                      ▼
               PersonaRepository
                      │
                      ▼
                  SQL Server
```

Este flujo tiene una ventaja muy importante.

El `Handler` **nunca recibe datos inválidos**.

Eso simplifica mucho el código del caso de uso.

# ¿Qué valida FluentValidation?

Esta es una de las dudas más importantes del curso.

Muchos desarrolladores intentan validar absolutamente todo con FluentValidation.

Eso es un error.

Debemos separar dos conceptos:

## Validaciones de entrada (Application)

Son las que hace FluentValidation.

Ejemplos:

* El nombre es obligatorio.
* El correo tiene un formato válido.
* La edad es mayor que cero.
* El NIT tiene una longitud válida.
* El código DANE tiene exactamente 5 caracteres.
* El municipio fue informado.
* La lista de detalles no está vacía.

Estas validaciones verifican que la solicitud tenga la forma esperada antes de ejecutar el caso de uso.

---

## Reglas del negocio (Domain)

Estas pertenecen al dominio.

Ejemplos:

* Un cliente bloqueado no puede generar facturas.
* Una factura cerrada no puede modificarse.
* Un producto descontinuado no puede venderse.
* Un empleado no puede aprobar su propia solicitud.
* Una persona jurídica debe tener representante legal.

Estas reglas protegen la consistencia del negocio y deben vivir en las entidades o servicios del dominio, no en los validadores.

---

# Ejemplo aplicado a TribuSoft

Supongamos este comando.

```csharp
public sealed class CrearPersonaNaturalCommand
{
    public string Nombre { get; init; }

    public string PrimerApellido { get; init; }

    public string NumeroDocumento { get; init; }

    public string Email { get; init; }

    public string CodigoMunicipio { get; init; }
}
```

¿Qué validará FluentValidation?

✔ Nombre obligatorio.

✔ Apellido obligatorio.

✔ Documento obligatorio.

✔ Documento con longitud válida.

✔ Email válido.

✔ Municipio informado.

¿Qué **no** debería validar?

❌ Si la persona puede celebrar contratos.

❌ Si el cliente tiene cartera vencida.

❌ Si el tercero está suspendido.

❌ Si la empresa está activa.

Esas son reglas del dominio.

# ¿Dónde vive el Validator?

En tu solución actual de TribuSoft:

```text
TribuSoft.Application
│
├── Commands
├── Queries
├── DTOs
├── Validators
│   ├── CrearPersonaNaturalValidator.cs
│   ├── ActualizarPersonaNaturalValidator.cs
│   ├── CrearMunicipioValidator.cs
│   ├── CrearDepartamentoValidator.cs
│   └── ...
├── Interfaces
└── Behaviors
```

Esta ubicación mantiene la capa **Application** responsable de validar la entrada de los casos de uso, mientras que **Domain** permanece libre de dependencias de FluentValidation.
