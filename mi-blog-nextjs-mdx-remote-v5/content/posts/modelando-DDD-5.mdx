> en las respuesta que teniamos como logico falso o verdadero ahora hay que agregar una tercera opcion, osea que ahora quedaria de la siguiente forma: Corrrecto, NO correcto, No aplica en preguntas como: Ajuste de tortillería, como quedaria ahora el tipo de respuesta ?


Exactamente. En ese caso **ya no es correcto modelarlo como `bool`**, porque `true/false` solamente representa dos estados.

Para una pregunta como:

> **Ajuste de tornillería**

tienes tres resultados de negocio:

```text
Correcto
No correcto
No aplica
```

Yo lo modelaría como un **tipo de respuesta de selección/estado**, no como booleano.

### 1. Crear un tipo específico

En C# 14 puedes comenzar sencillamente con un `enum`:

```csharp
public enum ResultadoInspeccion
{
    Correcto = 1,
    NoCorrecto = 2,
    NoAplica = 3
}
```

Entonces el parámetro de respuesta sería:

```csharp
public class ParametroRespuesta
{
    public Guid Id { get; private set; }

    public string Nombre { get; private set; }

    public TipoDatoRespuesta TipoDato { get; private set; }

    public string? Unidad { get; private set; }

    public bool Obligatorio { get; private set; }

    public int Orden { get; private set; }

    // ...
}
```

Y `TipoDatoRespuesta` podría evolucionar a:

```csharp
public enum TipoDatoRespuesta
{
    Boolean = 1,
    Decimal = 2,
    Entero = 3,
    Texto = 4,
    ResultadoInspeccion = 5
}
```

Pero aquí haría una **mejora de diseño importante**.

---

## 2. No llamaría a esto `Boolean`

En nuestro modelo anterior teníamos:

```text

Decimal
Entero
Texto
```

Ahora tenemos:

```text

```

porque:

```text

```

no significa realmente:

> verdadero/falso.

Representa un **resultado de inspección**.

Por ejemplo:

```text

ResultadoInspeccion.Correcto
```

o:

```text

```

o:

```text
ResultadoInspeccion.NoAplica
```

# 3. Pero hay una cuestión más importante

Yo no limitaría `TipoDatoRespuesta` únicamente a los tipos de C#.

Porque en tu sistema HVAC realmente estás describiendo **tipos de respuesta del negocio**.

Por ejemplo:

| Actividad              | Tipo de respuesta    |
| ---------------------- | -------------------- |
| Ajuste de tornillería  | Resultado inspección |
| ¿Equipo encendido?     | Sí/No                |
| Presión de descarga    | Decimal              |
| Temperatura de retorno | Decimal              |
| Observaciones          | Texto                |
| Amperaje RS/RT/ST      | Decimal compuesto    |

Entonces podríamos tener:

```csharp
public enum TipoRespuesta
{
    SiNo = 1,
    ResultadoInspeccion = 2,
    Decimal = 3,
    Entero = 4,
    Texto = 5,
    Compuesta = 6
}
```

Esto me parece **más apropiado para tu dominio** que llamarlo `TipoDatoRespuesta`.

Porque el sistema no está simplemente preguntando:

> ¿Qué tipo de dato C# voy a guardar?

Está preguntando:

> **¿Qué clase de respuesta espera esta actividad?**

---

# 4. ¿Y qué hacemos con `No aplica`?

Aquí aparece una distinción muy importante.

`No aplica` **no es lo mismo que una respuesta vacía o `null`**.

Por ejemplo:

### Caso 1

```text
Ajuste de tornillería
→ Correcto
```

Significa:

> La actividad fue aplicable y estaba correcta.

### Caso 2

```text
Ajuste de tornillería
→ No correcto
```

Significa:

> La actividad era aplicable pero se encontró un problema.

### Caso 3

```text
Ajuste de tornillería
→ No aplica
```

Significa:

> La actividad no corresponde a ese equipo o situación.

Por eso **no recomiendo utilizar `null` para representar `No aplica`**.

---

# 5. Esto incluso puede tener reglas de dominio

Por ejemplo:

```csharp
public enum ResultadoInspeccion
{
    Correcto = 1,
    NoCorrecto = 2,
    NoAplica = 3
}
```

Podríamos posteriormente agregar comportamiento:

```csharp
public static bool EsConforme(
    ResultadoInspeccion resultado)
{
    return resultado == ResultadoInspeccion.Correcto
        || resultado == ResultadoInspeccion.NoAplica;
}
```

Aunque aquí habría que analizar la regla real del negocio: en algunos procesos `No aplica` puede significar que la actividad no debe evaluarse, no necesariamente que el equipo sea "conforme".

# 11. `ParametroRespuesta`

Ahora creamos la definición de **qué debe responder el técnico**.

```csharp
using TribuSoft.Domain.Enums;

namespace TribuSoft.Domain.Entities;

public class ParametroRespuesta
{
    public Guid Id { get; private set; }

    public string Nombre { get; private set; } = null!;

    public TipoRespuesta TipoRespuesta { get; private set; }

    public string? Unidad { get; private set; }

    public bool Obligatorio { get; private set; }

    public int Orden { get; private set; }

    private ParametroRespuesta()
    {
    }

    public ParametroRespuesta(
        string nombre,
        TipoRespuesta tipoRespuesta,
        string? unidad,
        bool obligatorio,
        int orden)
    {
        if (string.IsNullOrWhiteSpace(nombre))
            throw new ArgumentException(
                "El nombre del parámetro es obligatorio.",
                nameof(nombre));

        if (orden < 1)
            throw new ArgumentOutOfRangeException(
                nameof(orden));

        Id = Guid.NewGuid();
        Nombre = nombre;
        TipoRespuesta = tipoRespuesta;
        Unidad = unidad;
        Obligatorio = obligatorio;
        Orden = orden;
    }
}
```

# 13. `ActividadCatalogo`

Ahora podemos construir nuestro primer Aggregate Root.

```csharp
using TribuSoft.Domain.Enums;

namespace TribuSoft.Domain.Entities;

public class ActividadCatalogo
{
    public Guid Id { get; private set; }

    public string Nombre { get; private set; } = null!;

    public string? Descripcion { get; private set; }

    private readonly List<ParametroRespuesta> _parametrosRespuesta = [];

    public IReadOnlyCollection<ParametroRespuesta>
        ParametrosRespuesta =>
        _parametrosRespuesta.AsReadOnly();

    private readonly List<EtapaActividad> _etapas = [];

    public IReadOnlyCollection<EtapaActividad>
        Etapas =>
        _etapas.AsReadOnly();

    private ActividadCatalogo()
    {
    }

    public ActividadCatalogo(
        string nombre,
        string? descripcion = null)
    {
        if (string.IsNullOrWhiteSpace(nombre))
            throw new ArgumentException(
                "El nombre de la actividad es obligatorio.",
                nameof(nombre));

        Id = Guid.NewGuid();
        Nombre = nombre;
        Descripcion = descripcion;
    }

    public void AgregarParametro(
        ParametroRespuesta parametro)
    {
        ArgumentNullException.ThrowIfNull(parametro);

        if (_parametrosRespuesta.Any(
                p => p.Nombre.Equals(
                    parametro.Nombre,
                    StringComparison.OrdinalIgnoreCase)))
        {
            throw new DomainException(
                $"El parámetro '{parametro.Nombre}' ya existe.");
        }

        _parametrosRespuesta.Add(parametro);
    }

    public void AgregarEtapa(
        EtapaMantenimiento etapa)
    {
        if (_etapas.Any(e => e.Etapa == etapa))
        {
            throw new DomainException(
                $"La etapa '{etapa}' ya está configurada.");
        }

        _etapas.Add(
            new EtapaActividad(etapa));
    }
}
```

Aquí estamos aplicando algo importante:

```csharp
private readonly List<ParametroRespuesta> _parametrosRespuesta = [];
```

pero afuera solamente exponemos:

```csharp
IReadOnlyCollection<ParametroRespuesta>
```

Por lo tanto, el consumidor no puede modificar directamente la colección.

Debe utilizar:

```csharp
actividad.AgregarParametro(...);
```

Eso protege las reglas del Aggregate.

# 15. Ahora viene `ActividadRealizada`

Esta representa la ejecución de una actividad específica.

```csharp
namespace TribuSoft.Domain.Entities;

public class ActividadRealizada
{
    public Guid Id { get; private set; }

    public Guid ActividadCatalogoId { get; private set; }

    private readonly List<Medicion> _mediciones = [];

    public IReadOnlyCollection<Medicion> Mediciones =>
        _mediciones.AsReadOnly();

    private ActividadRealizada()
    {
    }

    public ActividadRealizada(
        Guid actividadCatalogoId)
    {
        if (actividadCatalogoId == Guid.Empty)
            throw new ArgumentException(
                "La actividad de catálogo es obligatoria.",
                nameof(actividadCatalogoId));

        Id = Guid.NewGuid();

        ActividadCatalogoId =
            actividadCatalogoId;
    }

    public void AgregarMedicion(
        Medicion medicion)
    {
        ArgumentNullException.ThrowIfNull(medicion);

        if (_mediciones.Any(
                m => m.Etapa == medicion.Etapa))
        {
            throw new DomainException(
                $"Ya existe una medición para la etapa '{medicion.Etapa}'.");
        }

        _mediciones.Add(medicion);
    }
}
```

Aquí aparece una regla interesante:

```csharp
if (_mediciones.Any(
    m => m.Etapa == medicion.Etapa))
```

Estamos diciendo:

> No puede haber dos mediciones `Antes` para la misma actividad realizada.

Pero **ojo**: esta regla solamente será correcta si nuestro negocio realmente establece una medición por etapa.

Si posteriormente descubrimos que puede haber:

```text
Antes 1
Antes 2
Después 1
Después 2
```

tendremos que modificar esta regla.

Esto es precisamente por lo que estamos diseñando el dominio antes de hacer las tablas.

# 17. `ValorRespuesta`

Aquí tenemos que tomar una decisión importante.

Para mantener el modelo sencillo inicialmente:

```csharp
namespace TribuSoft.Domain.Entities;

public class ValorRespuesta
{
    public Guid Id { get; private set; }

    public Guid ParametroRespuestaId { get; private set; }

    public string Valor { get; private set; } = null!;

    private ValorRespuesta()
    {
    }

    public ValorRespuesta(
        Guid parametroRespuestaId,
        string valor)
    {
        if (parametroRespuestaId == Guid.Empty)
            throw new ArgumentException(
                "El parámetro es obligatorio.",
                nameof(parametroRespuestaId));

        if (string.IsNullOrWhiteSpace(valor))
            throw new ArgumentException(
                "El valor es obligatorio.",
                nameof(valor));

        Id = Guid.NewGuid();

        ParametroRespuestaId =
            parametroRespuestaId;

        Valor = valor;
    }
}
```

**Pero no considero esta versión definitiva.**

¿Por qué?

Porque ahora tenemos:

```text
Valor = "20.1"
Valor = "Correcto"
Valor = "No aplica"
Valor = "Observación..."
```

Todo como `string`.

Eso funciona técnicamente, pero perdemos parte de la seguridad del dominio.

# 18. El siguiente paso importante

Tenemos dos caminos:

### Opción A — valor tipado

```text
ValorBoolean
ValorDecimal
ValorEntero
ValorTexto
```

### Opción B — Value Objects / polimorfismo

Algo conceptualmente así:

```text
ValorRespuesta
    │
    ├── ValorBoolean
    ├── ValorDecimal
    ├── ValorEntero
    ├── ValorTexto
    └── ValorResultadoInspeccion
```

Para tu proyecto **me inclino por la opción B**, pero no quiero implementarla todavía sin analizar cómo queremos persistirla con EF Core 10.

Además, tenemos otro punto que debemos resolver antes de cerrar el modelo:

> **`Correcto / No correcto / No aplica` no necesariamente debería ser un `enum` fijo.**

Como ya vimos, mañana podrías tener:

```text
Bueno
Regular
Malo
No aplica
```

o:

```text
Sí
No
No aplica
```

y no sería buena práctica tener que modificar el código C# cada vez que el administrador cree una nueva opción.

Por eso el siguiente paso natural sería crear:

```text
TipoRespuesta
       │
       └── OpcionesRespuesta
               │
               ├── Correcto
               ├── No correcto
               └── No aplica
```

De esa manera **las opciones pertenecen al catálogo de actividades y no al código C#**.

Y esto nos permitirá modelar correctamente tanto:

```text
Ajuste de tornillería
→ Correcto / No correcto / No aplica
```

como:

```text
Estado filtro
→ Limpio / Sucio / No aplica
```

sin crear un nuevo `enum` para cada caso.
