# 2. Primero: ¿qué es un test?

Un test automático comprueba que nuestro código se comporta como esperamos.

Por ejemplo, supongamos que una orden de trabajo tiene una regla:

> Una orden de trabajo no puede crearse sin un cliente.

Podríamos tener:

```csharp
public sealed class OrdenTrabajo
{
    public Guid Id { get; private set; }
    public Guid ClienteId { get; private set; }

    private OrdenTrabajo()
    {
    }

    public OrdenTrabajo(Guid clienteId)
    {
        if (clienteId == Guid.Empty)
            throw new DomainException("El cliente es obligatorio.");

        Id = Guid.NewGuid();
        ClienteId = clienteId;
    }
}
```

Queremos demostrar automáticamente que:

```text
cliente válido
    ↓
OrdenTrabajo
    ↓
se crea correctamente
```

y:

```text
Guid.Empty
    ↓
OrdenTrabajo
    ↓
DomainException
```

Eso es testing.

Si nuestra solución es:

```text
TribuSoft
│
├── TribuSoft.Api
├── TribuSoft.Application
├── TribuSoft.Domain
└── TribuSoft.Infrastructure
```

yo agregaría:

```text
TribuSoft
│
├── src
│   ├── TribuSoft.Api
│   ├── TribuSoft.Application
│   ├── TribuSoft.Domain
│   └── TribuSoft.Infrastructure

└── tests
    ├── TribuSoft.Domain.Tests
    ├── TribuSoft.Application.Tests
    ├── TribuSoft.Infrastructure.Tests
    └── TribuSoft.Api.Tests
```

La relación conceptual sería:

```text
                 ┌──────────────────────┐
                 │   TribuSoft.Domain   │
                 └──────────┬───────────┘
                            │
                     Domain.Tests
                            │
                 ┌──────────▼───────────┐
                 │ TribuSoft.Application│
                 └──────────┬───────────┘
                            │
                  Application.Tests
                            │
                 ┌──────────▼───────────┐
                 │   Infrastructure     │

                            │
```

Esto es importante:

**cada proyecto de producción tiene su estrategia de pruebas correspondiente.**

# 4. Empezamos por Unit Testing

Para comenzar vamos a utilizar **xUnit**.

En .NET 10 puedes crear un proyecto de tests:

```bash
dotnet new xunit -n TribuSoft.Domain.Tests
```

Y agregarlo a la solución:

```bash
dotnet sln add tests/TribuSoft.Domain.Tests
```

Después hacemos referencia al proyecto Domain:

```bash
dotnet add tests/TribuSoft.Domain.Tests reference src/TribuSoft.Domain
```

La estructura queda:

```text
TribuSoft.Domain
    └── Entities
        └── OrdenTrabajo.cs

TribuSoft.Domain.Tests
    └── Entities
        └── OrdenTrabajoTests.cs
```

# 5. Nuestro primer test

Supongamos:

```csharp
public sealed class OrdenTrabajo
{
    public Guid Id { get; private set; }

    public Guid ClienteId { get; private set; }

    public OrdenTrabajo(Guid clienteId)
    {
        if (clienteId == Guid.Empty)
            throw new DomainException("El cliente es obligatorio.");

        Id = Guid.NewGuid();
        ClienteId = clienteId;
    }
}
```

El test:

```csharp
public class OrdenTrabajoTests
{
    [Fact]
    public void Crear_DeberiaCrearOrdenCuandoClienteEsValido()
    {
        // Arrange
        var clienteId = Guid.NewGuid();

        // Act
        var orden = new OrdenTrabajo(clienteId);

        // Assert
        Assert.NotEqual(Guid.Empty, orden.Id);
        Assert.Equal(clienteId, orden.ClienteId);
    }
}
```

Aquí aparece un concepto fundamental:

## AAA

Todo test debería intentar seguir:

```text
Arrange
   ↓
Act
   ↓
Assert
```

### Arrange

Preparar los datos:

```csharp
var clienteId = Guid.NewGuid();
```

### Act

Ejecutar aquello que queremos probar:

```csharp
var orden = new OrdenTrabajo(clienteId);
```

### Assert

Comprobar el resultado:

```csharp
Assert.Equal(clienteId, orden.ClienteId);
```

# 6. Otro test muy importante

Ahora probemos nuestra regla de dominio:

> No se puede crear una orden sin cliente.

```csharp
[Fact]
public void Crear_DeberiaLanzarExcepcionCuandoClienteNoEsValido()
{
    // Arrange
    var clienteId = Guid.Empty;

    // Act
    var action = () => new OrdenTrabajo(clienteId);

    // Assert
    var exception = Assert.Throws<DomainException>(action);

    Assert.Equal(
        "El cliente es obligatorio.",
        exception.Message);
}
```

Este test es **muy importante en DDD**.

¿Por qué?

Porque estamos probando una **regla del dominio**.

No estamos probando:

* EF Core
* SQL Server
* PostgreSQL
* HTTP
* Controllers
* JSON
* Repository

Estamos probando exclusivamente:

> **¿El dominio protege sus invariantes?**

---

# 7. Este es uno de los conceptos más importantes de DDD + Testing

Supongamos que tenemos:

```text
OrdenTrabajo
```

con estas reglas:

```text
✓ debe tener cliente
✓ debe tener técnico
✓ no puede cerrarse sin actividades
✓ no puede cancelarse después de cerrada
✓ no puede tener importe negativo
```

Cada regla debería tener tests.

Por ejemplo:

```text
OrdenTrabajoTests
│
├── Crear_DeberiaCrearOrdenCuandoDatosValidos
├── Crear_DeberiaFallarCuandoClienteNoExiste
├── Crear_DeberiaFallarCuandoTecnicoNoExiste
├── AgregarActividad_DeberiaAgregarActividad
├── Cerrar_DeberiaCerrarOrdenCuandoTieneActividades
├── Cerrar_DeberiaFallarCuandoNoTieneActividades
└── Cancelar_DeberiaFallarCuandoOrdenEstaCerrada
```

Observa algo:

Los nombres de los tests **describen comportamiento**, no implementación.

Eso es excelente para DDD.

# 8. Test de una regla de negocio

Supongamos que tenemos:

```csharp
public void Cerrar()
{
    if (_actividades.Count == 0)
        throw new DomainException(
            "La orden debe tener al menos una actividad.");

    Estado = EstadoOrden.Cerrada;
}
```

Test:

```csharp
[Fact]
public void Cerrar_DeberiaFallarCuandoNoTieneActividades()
{
    // Arrange
    var orden = CrearOrdenValida();

    // Act
    var action = () => orden.Cerrar();

    // Assert
    var exception = Assert.Throws<DomainException>(action);

    Assert.Equal(
        "La orden debe tener al menos una actividad.",
        exception.Message);
}
```

Aquí aparece una idea fundamental:

> **Los tests de Domain deberían proteger las reglas de negocio.**

---

# 9. ¿Qué NO deberíamos hacer?

Un error común sería crear tests así:

```csharp
[Fact]
public void ClienteId_DeberiaSerPrivateSet()
{
    // ...
}
```

Eso prueba detalles de implementación.

No nos interesa.

Nos interesa:

```text
¿Puede crearse una orden correctamente?
¿Puede cerrarse?
¿Puede cancelarse?
¿Se respetan las reglas?
```

DDD está muy orientado a **comportamiento**.

Por eso los tests deberían seguir ese mismo enfoque.

# 10. Unit Test vs Integration Test

Esta diferencia es fundamental.

### Unit Test

Prueba una unidad aislada:

```text
OrdenTrabajo
     ↓
reglas de negocio
```

No necesita:

```text
SQL Server
PostgreSQL
EF Core
HTTP
```

Por eso es rápido.

---

### Integration Test

Comprueba que varias partes funcionan juntas:

```text
API
 ↓
Application
 ↓
Infrastructure
 ↓
EF Core
 ↓
PostgreSQL
```

Aquí sí podemos utilizar una base de datos.

Por ejemplo:

```text
POST /api/ordenes-trabajo
             ↓
CreateOrdenTrabajoCommand
             ↓
Handler
             ↓
Repository
             ↓
EF Core
             ↓
PostgreSQL
```

Ese test comprueba integración.

# 11. En Clean Architecture tendremos diferentes niveles

Piensa en una pirámide:

```text
                 /\
                /  \
               / API\
              /------\
             /Integration\
            /--------------\
           / Application    \
          /------------------\
         /     Domain         \
        /______________________\
```

La mayor cantidad de tests normalmente estará abajo.

### Domain

Muchos tests:

```text
★★★★★
```

### Application

Bastantes:

```text
★★★★☆
```

### Infrastructure

Algunos tests de integración:

```text
★★★☆☆
```

### API

Tests de integración:

```text
★★☆☆☆
```

No queremos tener toda la aplicación probada únicamente desde HTTP.

```text

```

Ese es el siguiente nivel.

Para que realmente lo aprendas, podemos construir los tests alrededor de este dominio:

```text
Sistema de órdenes de trabajo
```

Y vamos a terminar con algo parecido a:

```text
TribuSoft
│

│   ├── TribuSoft.Domain
│   │   ├── Entities

│   │   ├── Enums
│   │   ├── Exceptions
│   │   └── Events
```
