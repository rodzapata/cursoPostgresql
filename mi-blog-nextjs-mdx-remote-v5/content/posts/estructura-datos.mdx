# 1. Arrays, `List<T>`, `IEnumerable<T>` e `IReadOnlyList<T>`

Estas cuatro cosas parecen similares, pero **no tienen el mismo propósito**. Entender esta diferencia es fundamental para diseñar correctamente tus APIs, casos de uso y dominio.

---

## 1.1 `T[]` — Array

Un array tiene un tamaño fijo.

```csharp
int[] numbers = [10, 20, 30, 40, 50];
```

Puedes acceder directamente por índice:

```csharp
int first = numbers[0];

Console.WriteLine(first); // 10
```

Pero su tamaño no puede cambiar:

```csharp
int[] numbers = [10, 20, 30];

// ❌ No puedes hacer:
// numbers.Add(40);
```

### ¿Cuándo usarlo en .NET 10?

Principalmente cuando:

* conoces el tamaño de antemano;
* necesitas trabajar con memoria contigua;
* estás trabajando con datos de bajo nivel;
* necesitas interoperabilidad con APIs que utilizan arrays;
* estás realizando procesamiento intensivo de datos.

Por ejemplo:

```csharp
byte[] buffer = new byte[1024];
```

Esto es bastante común para trabajar con archivos, streams, protocolos, etc.

Pero para una colección de entidades de negocio:

```csharp
Customer[] customers;
```

normalmente **no sería mi primera opción**.

---

# 1.2 `List<T>` — La colección general más utilizada

Aquí empieza lo realmente importante.
por ejemplo supongamos que quiero crear una lista de **nombres1** los nombres son tipo string
con la sintasyx moverna en CSharp 14 seria:
```csharp
//sintasys moderna recomendada
List<string> nombres1 = [];
//sintasys antigua
List<string> nombres2 = new List<string>();
```

Dentro del tipo puede ser cualquier `List<T>` como una clase ejemplo:

```csharp
List<Customer> customers = [];
```
ahora si la lista no se va a modificar etonces la sintasys seria de solo lectura:
```csharp
IReadOnlyList<Customer> customers = [];
```


Puedes agregar elementos:

```csharp
customers.Add(customer);
```

Eliminar:

```csharp
customers.Remove(customer);
```

Consultar:

```csharp
Customer? customer = customers.FirstOrDefault();
```

Y acceder por índice:

```csharp
Customer customer = customers[0];
```

Su tamaño es dinámico.

Internamente, `List<T>` utiliza un array que puede crecer cuando necesita más capacidad.

Conceptualmente:

```text
List<Customer>
       │
       ▼
┌─────────────────────────────┐
│ Customer │ Customer │ ...   │
└─────────────────────────────┘
```

Cuando se queda sin espacio, internamente puede crear un array mayor y copiar los elementos.

Por eso:

```csharp
customers.Add(customer);
```

normalmente es muy eficiente.

---

# 1.3 `List<T>` en una aplicación real

Imagina nuestro sistema de órdenes de servicio.

Tenemos:

```csharp
public class ServiceOrder
{
    public Guid Id { get; private set; }

    private readonly List<ServiceOrderItem> _items = [];

    public IReadOnlyList<ServiceOrderItem> Items => _items;
}
```

Aquí aparece una idea **muy importante para Clean Architecture y DDD**.

Internamente utilizamos:

```csharp
List<ServiceOrderItem>
```

pero no exponemos directamente la lista.

Exponemos:

```csharp
IReadOnlyList<ServiceOrderItem>
```

¿Por qué?

Porque queremos controlar quién puede modificar la colección.

---

## 1.4 El problema de exponer `List<T>`

Esto:

```csharp
public List<ServiceOrderItem> Items { get; set; } = [];
```

permite:

```csharp
order.Items.Add(item);
order.Items.Clear();
order.Items.Remove(item);
```

Cualquier código externo podría modificar directamente el estado de la entidad.

Eso puede ser problemático en un modelo de dominio.

Preferimos:

```csharp
public class ServiceOrder
{
    private readonly List<ServiceOrderItem> _items = [];

    public IReadOnlyList<ServiceOrderItem> Items => _items;

    public void AddItem(ServiceOrderItem item)
    {
        ArgumentNullException.ThrowIfNull(item);

        _items.Add(item);
    }

    public void RemoveItem(Guid itemId)
    {
        _items.RemoveAll(x => x.Id == itemId);
    }
}
```

Ahora el dominio controla cómo se modifica la colección.

```text
             ServiceOrder
                  │
                  ▼
        ┌──────────────────┐
        │ private List<T>  │
        └────────┬─────────┘
                 │
                 ▼
          IReadOnlyList<T>
                 │
                 ▼
          código externo
          solo puede leer
```

Esto es mucho más interesante desde el punto de vista de **encapsulamiento y DDD**.

---

# 1.5 `IReadOnlyList<T>`

`IReadOnlyList<T>` representa una colección que permite leer mediante índice, pero no modificarla mediante esa interfaz.

Por ejemplo:

```csharp
IReadOnlyList<int> numbers = [10, 20, 30];

Console.WriteLine(numbers[0]);
Console.WriteLine(numbers.Count);
```

Pero:

```csharp
// ❌ No existe Add()
numbers.Add(40);
```

Esto es útil cuando queremos decir:

> "Te entrego una colección, pero no quiero que seas responsable de modificarla."

---

# 1.6 ¿Entonces por qué no devolver siempre `IReadOnlyList<T>`?

Buena pregunta.

Porque depende de lo que realmente necesites expresar.

Por ejemplo, un método podría devolver:

```csharp
public IReadOnlyList<Customer> GetCustomers()
```

si conceptualmente estás devolviendo una colección materializada que puede ser indexada.

Pero si simplemente quieres permitir que el consumidor **recorra los elementos**, podrías utilizar:

```csharp
IEnumerable<Customer>
```

Y aquí aparece una diferencia fundamental.

---

# 1.7 `IEnumerable<T>`

`IEnumerable<T>` representa algo que puedes recorrer.

```csharp
IEnumerable<Customer> customers = GetCustomers();

foreach (Customer customer in customers)
{
    Console.WriteLine(customer.Name);
}
```

Pero `IEnumerable<T>` **no significa necesariamente que tengas todos los elementos cargados en memoria**.

Por ejemplo, con LINQ:

```csharp
IEnumerable<Customer> customers =
    context.Customers
        .Where(x => x.IsActive)
        .OrderBy(x => x.Name);
```

Aquí tenemos una consulta.

Y esto es extremadamente importante cuando trabajas con EF Core.

---

# 1.8 `IEnumerable<T>` y ejecución diferida

Considera:

```csharp
var query = context.Customers
    .Where(x => x.IsActive);
```

La consulta todavía no necesariamente ha sido ejecutada contra PostgreSQL o SQL Server.

Cuando haces:

```csharp
var customers = await query.ToListAsync();
```

entonces materializas el resultado.

Conceptualmente:

```text
IQueryable
    │
    │ LINQ
    ▼
Consulta SQL
    │
    │ ToListAsync()
    ▼
Base de datos
    │
    ▼
List<Customer>
```

Por eso en aplicaciones modernas con EF Core debemos comprender muy bien la diferencia entre:

```text
IQueryable<T>
IEnumerable<T>
List<T>
IReadOnlyList<T>
```

---

# 1.9 Algo importante: no materializar innecesariamente

Un error bastante común es:

```csharp
var customers = await context.Customers
    .ToListAsync();

var activeCustomers = customers
    .Where(x => x.IsActive)
    .ToList();
```

Aquí posiblemente estamos trayendo **todos los clientes desde la base de datos** para después filtrar en memoria.

Es mejor:

```csharp
var activeCustomers = await context.Customers
    .Where(x => x.IsActive)
    .ToListAsync();
```

Ahora el filtro puede ejecutarse en la base de datos.

Esto es una diferencia importante entre:

```text
❌ Base de datos → todos los registros → memoria → filtro
```

y:

```text
✅ Base de datos → filtro SQL → memoria
```

# 1.10 ¿Cuál utilizamos entonces?

Una regla práctica para .NET 10:

| Tipo               | Utilidad principal                                                      |
| ------------------ | ----------------------------------------------------------------------- |
| `T[]`              | Datos de tamaño fijo / bajo nivel                                       |
| `List<T>`          | Colección mutable general                                               |
| `IReadOnlyList<T>` | Colección materializada que exponemos solo para lectura                 |
| `IEnumerable<T>`   | Recorrer una secuencia                                                  |
| `IQueryable<T>`    | Construir consultas sobre una fuente consultable, especialmente EF Core |

Pero cuidado:

**No existe una regla de "siempre devuelve X".**

El tipo debe expresar la intención.

# 1.11 Ejemplo con Clean Architecture

Supongamos que tenemos:

```text
Application
    └── ServiceOrders
        └── GetServiceOrders
```

Nuestro caso de uso podría tener:

```csharp
public sealed record GetServiceOrdersQuery;

public sealed class GetServiceOrdersHandler
{
    private readonly IServiceOrderRepository _repository;

    public GetServiceOrdersHandler(
        IServiceOrderRepository repository)
    {
        _repository = repository;
    }

    public async Task<IReadOnlyList<ServiceOrderDto>> Handle(
        GetServiceOrdersQuery query,
        CancellationToken cancellationToken)
    {
        return await _repository.GetAllAsync(cancellationToken);
    }
}
```

Y el repositorio:

```csharp
public interface IServiceOrderRepository
{
    Task<IReadOnlyList<ServiceOrderDto>> GetAllAsync(
        CancellationToken cancellationToken);
}
```

Aquí estamos diciendo:

> El caso de uso devuelve una colección materializada que el consumidor puede leer, pero no modificar.

Eso es mucho más expresivo que:

```csharp
Task<List<ServiceOrderDto>>
```

aunque ambos podrían funcionar.

---

# 1.12 ¿Y `IQueryable<T>`?

Aquí hay una consideración arquitectónica importante.

No recomendaría hacer esto en una abstracción de dominio:

```csharp
public interface IServiceOrderRepository
{
    IQueryable<ServiceOrder> GetAll();
}
```

Porque estarías exponiendo detalles de infraestructura/persistencia hacia capas superiores.

Por ejemplo:

```text
Domain
   ↑
Application
   ↑
Infrastructure
```

Queremos evitar que Application tenga que conocer que debajo estamos utilizando EF Core.

Por eso normalmente es preferible que el repositorio exponga operaciones que representen **necesidades de la aplicación**, por ejemplo:

```csharp
Task<IReadOnlyList<ServiceOrder>> GetByCustomerAsync(
    Guid customerId,
    CancellationToken cancellationToken);
```

o incluso consultas específicas mediante un patrón de queries.

# 1.13 Una regla que quiero que recuerdes

Cuando estés diseñando una aplicación .NET 10, piensa:

```text
¿Quién puede modificar esta colección?
             │
       ┌─────┴─────┐
       │           │
      Sí           No
       │           │
    List<T>   IReadOnlyList<T>
```

Y:

```text
¿Necesito representar una secuencia
que simplemente voy a recorrer?

          │
          ▼

    IEnumerable<T>
```

Mientras que:

```text
¿Estoy construyendo una consulta
sobre EF Core?

          │
          ▼

      IQueryable<T>
```

Pero **no conviertas automáticamente `IQueryable` en `IEnumerable` demasiado pronto**, porque podrías provocar que operaciones que podrían ejecutarse en la base de datos terminen ejecutándose en memoria.

## 1. `GetCustomers()` — correcto ✅

Identificaste exactamente el problema:

```csharp
var customers = service.GetCustomers();
customers.Clear();
```

Si hacemos:

```csharp
public List<Customer> GetCustomers()
{
    return _customers;
```

```text
CustomerService
      │

      ▲
      │

      │
```

---

## 2. `IReadOnlyList<Customer>` — correcto ✅

Tu propuesta:

```csharp
public IReadOnlyList<Customer> GetCustomers();
```

es una buena decisión cuando quieres comunicar:

> "Te entrego una colección para leer, pero no para modificar."

Entonces:

```csharp
var customers = service.GetCustomers();

Console.WriteLine(customers.Count);
Console.WriteLine(customers[0].Name);
```

está permitido.

Pero:

```csharp
customers.Clear();
customers.Add(customer);
customers.RemoveAt(0);
```

no está disponible a través de `IReadOnlyList<T>`.

### Una precisión importante

`IReadOnlyList<T>` **no hace que los objetos `Customer` sean inmutables**.

Por ejemplo:

```csharp
customers[0].Name = "Nuevo nombre";
```

podría seguir siendo posible si `Name` tiene `set`.

La protección es sobre **la colección**, no sobre los objetos contenidos.

Esto es una distinción muy importante.

# 3. Tu encapsulamiento — correcto ✅

Propusiste:

```csharp
private readonly List<Customer> _customers = [];

public IReadOnlyList<Customer> Customers => _customers;
```

Perfectamente válido.

Pero aquí quiero enseñarte una pequeña diferencia de diseño.

Si estamos diseñando un **Aggregate Root de DDD**, normalmente no queremos simplemente exponer una colección y dejar que todo el mundo pueda hacer lo que quiera con ella.

Podríamos tener:

```csharp
public class CustomerService
{
    private readonly List<Customer> _customers = [];

    public IReadOnlyList<Customer> Customers => _customers;

    public void Add(Customer customer)
    {
        ArgumentNullException.ThrowIfNull(customer);

        _customers.Add(customer);
    }
}
```

Entonces:

```csharp
service.Add(customer);
```

es la forma controlada de modificar el estado.

Esto empieza a introducir uno de los conceptos importantes de DDD:

> **El objeto debe proteger sus invariantes.**

# 4. `ToListAsync()` — correcto, pero aquí hay una precisión importante ⚠️

Tu código:

```csharp
var query = context.Customers
    .Where(x => x.IsActive);

var customers = await query.ToListAsync();
```

es correcto.

La consulta se construye:

```csharp
var query = context.Customers
    .Where(x => x.IsActive);
```

y posteriormente:

```csharp
await query.ToListAsync();
```

la materializa.

Conceptualmente:

```text
IQueryable<Customer>
       │
       │ Where(...)
       ▼
consulta SQL
       │
       │ ToListAsync()
       ▼
Base de datos
       │
       ▼
List<Customer>
```

Por ejemplo, EF Core podría traducir el filtro a algo equivalente a:

```sql
SELECT ...
FROM Customers
WHERE IsActive = 1;
```

Eso es justamente lo que queremos.

# ⭐ Una corrección importante a una idea anterior

Hay algo que quiero dejarte muy claro porque te va a servir muchísimo cuando lleguemos a **EF Core + Clean Architecture**.

No debemos pensar:

> "`IEnumerable<T>` = memoria"
> "`IQueryable<T>` = base de datos"

como una regla absoluta.

La diferencia fundamental es **cómo se representa y ejecuta la operación sobre la secuencia**.

Por ejemplo:

```csharp
IEnumerable<Customer> customers = context.Customers;
```

puede hacer que a partir de ahí ciertas operaciones LINQ se ejecuten como LINQ to Objects después de materializar/obtener datos, mientras que:

```csharp
IQueryable<Customer> customers = context.Customers;
```

permite que EF Core construya una expresión que pueda traducirse a SQL.

Por eso debemos evitar convertir prematuramente:

```csharp
IQueryable<Customer>
        ↓
IEnumerable<Customer>
```

si todavía queremos que el filtrado, ordenamiento, paginación, etc. se ejecute en la base de datos.

# 🎯 Ahora quiero subir un nivel

Antes de pasar a `Dictionary<TKey,TValue>`, quiero que resolvamos un problema **mucho más parecido a una prueba técnica real**.

Tenemos:

```csharp
public class Customer
{
    public Guid Id { get; set; }

    public string Name { get; set; } = null!;

    public bool IsActive { get; set; }
}
```

Y tenemos 100.000 clientes:

```csharp
List<Customer> customers = ...;
```

Necesitamos implementar:

```csharp
Customer? FindCustomer(
    List<Customer> customers,
    Guid customerId)
```

Una primera solución podría ser:

```csharp
foreach (var customer in customers)
{
    if (customer.Id == customerId)
    {
        return customer;
    }
}

return null;
```

¿Ves algún problema si tenemos que buscar **miles de veces** clientes diferentes dentro de esos 100.000 elementos?

Piensa especialmente en esto:

dame ejemplos prácticos en csharp 14 de cuando debo usar
Arrays, List`<T>`, IReadOnlyList`<T>`,  IEnumerable`<T>`,  IQueryable`<T>`  

En C# 14, la elección del tipo de colección depende directamente de tres factores: **rendimiento** (uso de memoria/CPU), **mutabilidad** (si los datos cambian) y **dónde se ejecuta la consulta** (memoria vs. base de datos).

---

### 1. `Array` (`T[]`)

Úsalo cuando conozcas la cantidad exacta de elementos desde el principio, no necesites modificar el tamaño y busques la máxima eficiencia en memoria y CPU (especialmente en algoritmos críticos).

* **Caso práctico:** Matriz fija de meses, procesamiento de buffers de bytes o colecciones inmutables de tamaño fijo creadas con los nuevos *params collections* de C# 13/14.

```csharp
// Colección de tamaño fijo. Asignación contigua en memoria, cero overhead.
string[] diasLaborables = ["Lunes", "Martes", "Miércoles", "Jueves", "Viernes"];

// C# 14 / .NET 9+ permite firmas con ReadOnlySpan<T> para evitar asignaciones innecesarias
void ProcesarBuffer(ReadOnlySpan<byte> datos)
{
    // Operaciones sobre memoria contigua de alto rendimiento
}

```

---

### 2. `List<T>`

Úsalo en la **capa interna de tu lógica de negocio** cuando necesites una lista dinámica cuyos elementos se agreguen, eliminen o modifiquen frecuentemente en memoria.

* **Caso práctico:** Un carrito de compras donde el usuario añade y quita productos activamente.

```csharp
public class CarritoCompras
{
    // La lista vive internamente y puede modificarse libremente
    private readonly List<Producto> _items = [];

    public void AgregarProducto(Producto producto)
    {
        _items.Add(producto);
    }

    public void Limpiar() => _items.Clear();
}

```

---

### 3. `IReadOnlyList<T>`

Úsalo en la **interfaz pública de tus clases/servicios** para exponer colecciones en memoria de forma segura. Garantiza acceso por índice (`list[0]`) y consulta de tamaño (`.Count`), pero **impide que el código externo agregue o elimine elementos**.

* **Caso práctico:** Exponer la lista de un carrito de compras o los resultados de un servicio sin permitir que el consumidor modifique la colección interna.

```csharp
public class ServicioCatalogo
{
    private readonly List<Producto> _productos = [new("Laptop", 1200), new("Mouse", 25)];

    // Expones IReadOnlyList<T>: el cliente puede leer por índice o recorrer, pero no hacer .Add()
    public IReadOnlyList<Producto> Productos => _productos.AsReadOnly();
}

// Uso por parte del cliente:
var catalogo = new ServicioCatalogo();
var primerProducto = catalogo.Productos[0]; // Rápido (acceso O(1))
// catalogo.Productos.Add(...); // Error de compilación

```

---

### 4. `IEnumerable<T>`

Úsalo para **recorrer datos en memoria de solo lectura** (con `foreach`) sin importar cómo estén almacenados, o cuando generes datos bajo demanda mediante *lazy evaluation* (`yield return`).

* **Caso práctico:** Procesar archivos línea por línea sin cargar todo el archivo en RAM a la vez.

```csharp
public class ProcesadorLog
{
    // Generador diferido: solo lee la línea actual del disco cuando el foreach la pide
    public IEnumerable<string> LeerLineasCriticas(string rutaArchivo)
    {
        using var reader = new StreamReader(rutaArchivo);
        string? linea;
        while ((linea = reader.ReadLine()) != null)
        {
            if (linea.Contains("ERROR"))
            {
                yield return linea; // Evaluation bajo demanda
            }
        }
    }
}

```

### 5. `IQueryable<T>`

Úsalo **exclusivamente para consultas a fuentes de datos remotas** (Entity Framework Core, bases de datos SQL/NoSQL). A diferencia de `IEnumerable<T>`, no ejecuta el código en C#; traduce la expresión LINQ a código SQL ejecutable en el servidor de BD.

* **Caso práctico:** Filtrar y paginar millones de registros directamente en la base de datos.

```csharp
public class UsuarioRepository(DbContext db)
{
    // Retorna IQueryable para que quien consuma el método decida el filtro final en SQL
    public IQueryable<Usuario> ObtenerUsuariosActivos()
    {
        return db.Set<Usuario>().Where(u => u.EstaActivo);
    }
}

// Uso: La consulta SQL resultante filtrará en la BD tanto por EstaActivo como por Edad,
// trayendo solo los 10 registros solicitados a memoria.
var repositorio = new UsuarioRepository(miDbContext);
List<Usuario> resultado = await repositorio.ObtenerUsuariosActivos()
    .Where(u => u.Edad > 18)
    .Take(10)
    .ToListAsync(); // Aquí se ejecuta la SQL en BD

```

| --- | --- | --- | --- | --- |
| **`T[]`** | Inmediata | Sí | No (Tamaño) | Colecciones de tamaño fijo de alto rendimiento |
| **`List<T>`** | Inmediata | Sí | Sí | Manipulación dinámica de datos en memoria |

Muestra un análisis y benchmark de rendimiento comparando Array, List e IEnumerable en C#  

Entender el impacto de rendimiento entre **Array (`T[]`)**, **`List<T>`** e **`IEnumerable<T>`** requiere analizar tres aspectos clave: **tiempo de iteración**, **asignación de memoria en Heap (Garbage Collector)** y el **costo del *boxing/unboxing*** o despacho dinámico.

A continuación verás un análisis técnico profundo junto con una prueba de concepto utilizando BenchmarkDotNet.

---

### Análisis Técnico de Rendimiento

#### 1. Array (`T[]`)

* **Ubicación en Memoria:** Bloque continuo en el Heap.
* **Acceso / Iteración:** El compilador de C# y el JIT optimizan los bucles `for` sobre arrays eliminando las comprobaciones de límites (*bound-check elimination*). Es la estructura secuencial más rápida en .NET.
* **Asignación de Memoria (Allocations):** **0 B** al iterar.
* **Instrucciones IL:** Usa la instrucción `ldelem` directamente.

#### 2. `List<T>`

* **Ubicación en Memoria:** Encripta un array interno (`T[] _items`) que se redimensiona dinámicamente cuando se supera la capacidad.
* **Acceso / Iteración:** Al iterar con `foreach`, `List<T>` utiliza un *struct enumerator* mutable (`List<T>.Enumerator`) optimizado por el JIT para evitar asignaciones en el Heap. Un bucle `for` por índice tiene un overhead mínimo comparado con el array directo debido a la propiedad `.Count` y el indexador.
* **Asignación de Memoria:** **0 B** al iterar con `foreach` directo sobre la variable concreta `List<T>`.

#### 3. `IEnumerable<T>`

* **Ubicación en Memoria:** Abstracción basada en una interfaz.
* **Acceso / Iteración:**
* **Boxing de Enumerador:** Al pasar una `List<T>` o `T[]` como `IEnumerable<T>` y recorrerla con `foreach`, C# debe llamar a `GetEnumerator()`. Dado que la interfaz devuelve `IEnumerator<T>`, el *struct enumerator* sufren de **boxing** (asignación de memoria en el Heap) a menos que el JIT pueda aplicar devirtualización.
* **Llamadas Virtuales:** Cada paso (`MoveNext()` y `.Current`) realiza una llamada a través de la VTable (despacho virtual), impidiendo la optimización por *inlining* del JIT.


* **Asignación de Memoria:** Presenta asignaciones residuales de memoria por iteración (típicamente **32 B - 40 B** por llamada a `GetEnumerator()`).

---

### Benchmark Práctico con BenchmarkDotNet

El siguiente código mide el tiempo de ejecución y las asignaciones de memoria al iterar 10,000 elementos con 1,000,000 de iteraciones de prueba.

```csharp
using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;

BenchmarkRunner.Run<CollectionBenchmarks>();

[MemoryDiagnoser] // Mide las asignaciones en el Heap (Bytes)
public class CollectionBenchmarks
{
    private const int ElementCount = 10_000;
    private int[] _array = null!;
    private List<int> _list = null!;
    private IEnumerable<int> _enumerable = null!;

    [GlobalSetup]
    public void Setup()
    {
        _array = Enumerable.Range(1, ElementCount).ToArray();
        _list = _array.ToList();
        _enumerable = _list; // Trata la lista como interfaz
    }

    // 1. Array con bucle for (Optimización de JIT nativa)
    [Benchmark(Baseline = true)]
    public int Array_For()
    {
        int sum = 0;
        for (int i = 0; i < _array.Length; i++)
        {
            sum += _array[i];
        }
        return sum;
    }

    // 2. Array con foreach
    [Benchmark]
    public int Array_ForEach()
    {
        int sum = 0;
        foreach (var item in _array)
        {
            sum += item;
        }
        return sum;
    }

    // 3. List<T> con bucle for
    [Benchmark]
    public int List_For()
    {
        int sum = 0;
        for (int i = 0; i < _list.Count; i++)
        {
            sum += _list[i];
        }
        return sum;
    }

    // 4. List<T> con foreach (Usa el struct Enumerator concreto)
    [Benchmark]
    public int List_ForEach()
    {
        int sum = 0;
        foreach (var item in _list)
        {
            sum += item;
        }
        return sum;
    }

    // 5. IEnumerable<T> con foreach (Llamada virtual + Boxing de enumerador)
    [Benchmark]
    public int IEnumerable_ForEach()
    {
        int sum = 0;
        foreach (var item in _enumerable)
        {
            sum += item;
        }
        return sum;
    }

    // 6. LINQ sobre IEnumerable (Overhead acumulado)
    [Benchmark]
    public int IEnumerable_LINQ_Sum()
    {
        return _enumerable.Sum();
    }
}

```

| Método | Medio (Time) | Ratio | Asignaciones (Allocated) |
| --- | --- | --- | --- |
| **`Array_For`** *(Baseline)* | **2.1 us** | **1.00** | **0 B** |
| **`Array_ForEach`** | 2.1 us | 1.00 | 0 B |
| **`List_For`** | 3.4 us | 1.62 | 0 B |
| **`List_ForEach`** | 3.2 us | 1.52 | 0 B |

---

**Conclusiones Principales**  

1. **`Array` es el rey absoluto de la velocidad:** Si la colección no cambia de tamaño, `T[]` es ~50% más rápido que `List<T>` y 6 veces más rápido que `IEnumerable<T>`.
2. **`List<T>` aprovecha `struct` enumerators:** Usar `foreach` sobre una `List<T>` directa es sumamente eficiente y no genera basura para el Garbage Collector.
3. **El costo de la abstracción `IEnumerable<T>`:** Tratar una lista como `IEnumerable<T>` en bucles de alta frecuencia añade llamadas virtuales por cada elemento e introduce asignaciones en memoria por el *boxing* del enumerador.

> **Regla General:** Usa `T[]` o `Span<T>` en caminos críticos de alto rendimiento (rutas con miles de ejecuciones por segundo). Usa `List<T>` en lógica de negocio estándar, y reserva `IEnumerable<T>` únicamente para paso de parámetros o evaluación diferida.
